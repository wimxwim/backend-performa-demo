### Tabel Generate Streaming — Hasil Real (3 Baris)

Jika pakai COPY 1.6 menit, mereka 25x lebih cepat bisa jualan — manfaat langsung ke komunitas. ### Penjelasan Singkat Tiap Konsep (Warung -> Teknikal)

**1. Streaming vs Array — Karung Dicicil 10k**

> Bayangkan warung: kamu punya 5 juta karung beras. Jika tumpuk semua di meja sekaligus (array), meja jebol OOM 9GB. Jika cicil 10 ribu per truk via streaming (Readable pipeline), meja tetap lega heap flat 64MB, RSS 210MB, selesai 99 detik. Secara teknikal ini adalah `Readable.from(generator) -> pipeline -> createWriteStream` — tidak simpan 5M object di RAM, tulis per 10k langsung ke file.

**2. COPY vs INSERT — Fotokopi vs Tulis Nota**

> Bayangkan warung: kamu harus catat 5 juta nota. Jika tulis satu-satu (INSERT batch 1000 x 5000 = 41 menit), tangan keriting. Jika fotokopi massal (COPY 1 pipeline TSV 1.6 menit), selesai 25x lebih cepat. Secara teknikal ini adalah `COPY FROM STDIN WITH (FORMAT csv, DELIMITER E'\t') via pg-copy-streams` 50k rows/s vs `prisma.$executeRawUnsafe INSERT` 2k rows/s.

**3. GIN trigram — Indeks Belakang Buku**

> Bayangkan warung: kamu cari "ayam" di buku 5 juta halaman. Jika baca semua halaman (Seq Scan 2000ms), seharian. Jika pakai indeks belakang buku (GIN trigram pecah jadi {aya, yam}, Bitmap Index Scan 10ms), langsung lompat halaman 12,45,89 — 200x lebih cepat. Secara teknikal ini adalah `CREATE EXTENSION pg_trgm; CREATE INDEX USING GIN (name gin_trgm_ops)` + `WHERE name % 'ayam' ORDER BY similarity DESC`.

**4. wal_level — CCTV Hemat vs Lengkap**

> Bayangkan warung: CCTV hemat (minimal) hanya rekam penting — hemat storage 34GB (2-4GB vs 38GB). CCTV lengkap (logical) rekam semua untuk replay/CDC — butuh storage besar tapi bisa replay ke ES/Kafka. Secara teknikal ini adalah `wal_level = minimal` untuk bulk hemat WAL vs `wal_level = logical` untuk Debezium CDC. Hemat untuk bulk, lengkap untuk produksi.

**5. shared_buffers — Meja Saji Besar 2GB**

> Bayangkan warung: meja saji kecil 256MB hanya muat 1 lauk — tiap ada pesanan bolak-balik gudang (read NVMe). Meja saji besar 2GB (15% RAM) muat banyak lauk populer — pesanan langsung saji dari meja, tidak bolak-balik gudang. Secara teknikal ini adalah `shared_buffers = 2GB` cache data/index di RAM + `effective_cache_size = 6GB` hint planner pilih Index Scan.

**6. UNLOGGED — Karung Tanpa Buku Dulu**

> Bayangkan warung: saat 5M karung masuk, jangan catat di buku dulu (UNLOGGED tanpa WAL) — catat setelah semua karung masuk (CREATE GIN + VACUUM ANALYZE). Jika catat per karung (GIN update per row), lambat 40 menit. Jika catat setelah semua masuk, 12 menit. Secara teknikal ini adalah `CREATE UNLOGGED TABLE umkm_staging (LIKE umkm INCLUDING ALL)` + `DROP INDEX idx_umkm_name_trgm` sebelum COPY + `CREATE INDEX USING GIN` sesudah.

**7. Jitter — Tabur Acak 1.1km**

> Bayangkan warung: kamu tabur beras di nampan — jika di satu titik, numpuk tidak natural. Jika tabur acak +-0.01 deg (~1.1km) dari center kelurahan, menyebar natural dalam bbox Pesanggrahan. Secara teknikal ini adalah `lat = centerLat + (Math.random()-0.5)*0.02` + `lng = centerLng + (Math.random()-0.5)*0.02` — agar uji ES `geo_distance 5km` bermakna, tidak semua titik di koordinat yang sama.

**8. Distribusi — Porsi Lauk Sesuai Pesanan**

> Bayangkan warung: kamu bagi lauk — jika asal bagi rata 20% per kelurahan, bohongi pesanan real. Jika porsi sesuai pesanan real (weighted random Bintaro 32%, Pesanggrahan 9.4% sesuai `Rekap_by_Kelurahan.csv`), jujur dan roadmap tepat. Secara teknikal ini adalah `weightedRandom([31.7, 27.8, 17.3, 13.5, 9.4])` — Bintaro paling banyak karena perumahan menengah-atas, Pesanggrahan paling sedikit karena pusat kecamatan.

### Swap 8G Setup — Wajib untuk 13GB RAM + 5M Index Build

File: `scripts/swap-setup.sh` (executable, idempotent).

```bash

```

Isi `scripts/swap-setup.sh`:

```bash
#!/bin/bash
# fallocate 8G /swapfile || dd if=/dev/zero of=/swapfile bs=1M count=8192
# chmod 600 /swapfile; mkswap /swapfile; swapon /swapfile
# echo '/swapfile none swap sw 0 0' | tee -a /etc/fstab
# sysctl -w vm.swappiness=10 vm.vfs_cache_pressure=50
# sysctl -w vm.dirty_background_bytes=536870912 vm.dirty_bytes=2147483648
# verifikasi: free -h; swapon --show
fallocate -l 8G /swapfile || dd if=/dev/zero of=/swapfile bs=1M count=8192
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl -w vm.swappiness=10
sysctl -w vm.vfs_cache_pressure=50
sysctl -w vm.dirty_background_bytes=536870912
sysctl -w vm.dirty_bytes=2147483648
free -h; swapon --show
```

Sysctl detail:

| Param | Nilai | Alasan 1 Baris |
|-------|-------|----------------|
| `vm.swappiness` | 10 | Jangan swap agresif, hanya saat RAM >90% |
| `vm.vfs_cache_pressure` | 50 | Pertahankan dentry/inode cache penting untuk banyak file WAL |
| `vm.dirty_background_bytes` | 512MB | Flush background tiap 512MB dirty |
| `vm.dirty_bytes` | 2GB | Throttle write jika dirty >2GB hindari stall 30 detik |

- [ ] `wal_level = replica` (atau `logical` jika pakai Debezium/Kafka CDC)
- [ ] `synchronous_commit = on`
- [ ] `max_wal_size = 1GB`, `min_wal_size = 80MB`, `checkpoint_timeout = 15min`
- [ ] `VACUUM ANALYZE` semua tabel setelah load
- [ ] `REFRESH MATERIALIZED VIEW CONCURRENTLY mv_kas_summary; REFRESH MATERIALIZED VIEW CONCURRENTLY mv_kas_total;`

💡 Hidden Gem — Kenapa `effective_io_concurrency = 200` untuk NVMe bukan 1: HDD hanya bisa 1-2 I/O paralel karena head fisik harus gerak — jadi default Postgres 1 masuk akal untuk HDD 2010. NVMe tidak punya head — ia punya 32+ queue x 64K depth, bisa 200 I/O paralel tanpa penalti seek. Jika kamu biarkan 1 di NVMe 1.3GB/s, kamu pakai Ferrari tapi gigi 1 — Bitmap Heap Scan yang seharusnya 10ms jadi 200ms karena planner kira random I/O mahal. Set 200 bukan "tuning agresif" — itu jujur ke hardware: NVMe random_page_cost 1.1 ~ seq_page_cost 1.0, jadi planner berani pilih Index Scan. Hidden gem-nya: tuning bukan soal "lebih besar lebih baik" — tapi soal jujur ke fisika hardware. HDD = 1, NVMe = 200, dan jika kamu salah, planner bohongi dirinya sendiri.

### Fabric 6 Layer 514 Node vs PG Hash Rp0 — Kapan Butuh Blockchain

| Dimensi | PG SHA-256 Hash Chain (MVP) | Hyperledger Fabric (Fase 5) |
|---------|-----------------------------|-----------------------------|
